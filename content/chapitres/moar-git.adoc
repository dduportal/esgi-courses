== Gestion de version décentralisée

* Chaque utilisateur maintient une version du dépôt _local_ qu'il peut changer à souhait
* Indépendant du commit, ils peuvent "pousser" une version sur un dépôt **distant**
* Un dépôt _local_ peut avoir plusieurs dépôts **distants**.

== Git Remote

Git permet de manipuler des "remotes"

* "Remote" == "Dépôt Distant" (sur un autre ordinateur)
* Chaque "Remote" possède sa propre arborescence
* Sous-commande `git remote ...`
* Un dépôt (local) peut posséder N remotes

== Afficher les Remotes

[source,bash]
--
git remote
# 1 seule remote : 'origin'

git remote -v
# 2 entrées : fetch / push
# Vous devriez voir l'URL de votre dépôt en tant que 'origin'
--

La commande 'git clone' a effectué l'action ci-dessous pour vous :

[source,bash]
--
git remote add origin <URL de votre dépôt>
--

== Publier une branche sur une remote

Maintenant qu'on a un dépôt, il faut publier notre code dessus !

[source, bash]
--
# git push <remote> <votre_branche_courante>
git push origin main
--

== Que s'est il passé ?

image:remote1.svg[]

== !

* `git` a envoyé la branche `main` sur le remote `origin`

* ... qui a accepté le changement et mis à jour sa propre branche main.
* `git` a créé localement une branche distante `origin/main` qui suit l'état de `main` sur le remote.

* Vous pouvez constater que la page github de votre dépôt affiche le code source

== Refaisons un commit !

[source, bash]
--

git commit --allow-empty -m "Yet another commit"
git push origin main
--

== Branches distantes

Dans votre dépôt local, une branche "distante" est automatiquement suivie par git

C'est une image du dernier état connu de la branche sur le remote.

[source, bash]
--
git branch
# Branches locales

git branch -r
# 'r' pour "remotes"

git branch -a
# 'a' pour "all"
--

== Récupérer la liste des changements

Pour mettre à jour les branches distantes depuis le remote il faut utiliser la commande `git fetch` :

[source, bash]
--
git fetch origin


git fetch --all --prune
# --all : toutes les remotes (pas seulement origin)
# --prune : kezako ?
--

== 🎓 Créez un commit depuis GitHub directement

* Cliquez sur le bouton éditer en haut à droite du "README"
* Changez le contenu de votre README
* Dans la section "Commit changes"
** Ajoutez un titre de commit et une description

** Cochez "Commit directly to the main branch"
** Validez

GitHub crée directement un commit sur la branche main sur le dépôt distant

== ✅ Rapatrier les changements distants

[source, bash]
--
# Met à jour les branches distantes du dépôt origin
git fetch origin

# La branche distante main a avancé sur le remote origin
# => La branche remotes/origin/main est donc mise à jour

# Ouvrez votre README
code ./README.md

# Mystère, le fichier README ne contient pas vos derniers changements?
git log

# Votre nouveau commit n'est pas présent, AHA !
git branch -a
--

== Branche Distante VS Branche Locale

Le changement a été rapatrié, cependant il n'est pas encore présent sur votre branche main locale

[source, bash]
--
# Merge la branche distante dans la branche locale.
git merge origin/main main
--

== !

Vu que votre branche main n'a pas divergé (== partage le même historique) de la branche distante, `git merge` effectue automatiquement un "fast forward".

[source, bash]
--
Updating 1919673..b712a8e
Fast-forward
 README.md | 1 +

 1 file changed, 1 insertion(+)
--

Cela signifie qu'il fait "avancer" la branche `main` sur le même commit que la branche `origin/main`

== !

== !

[source, bash]
--
# Liste l'historique de commit
git log
# Votre nouveau commit est présent sur la branche main !
# Juste au dessus de votre commit initial !
git branch -a
--

Et vous devriez voir votre changement dans le ficher README.md

== Un remote pour les gouverner tous

Tous les dévelopeu•se•r•s envoient leur commits et branches sur le même remote

* Simple a gérer ...
* ... mais nécessite que tous les contributeurs aient accès au dépôt
** Adapté a l'entreprise, peu adapté au monde de l'open source

== Chacun son propre remote

* La motivation: accès simplifié
** Tout le monde peut lire le dépôt principal. Personne ne peut écrire dessus.
** Tout le monde peut dupliquer le dépôt public et écrire sur sa copie.
** Toute modification du dépôt principal passe par une procédure de revue.
** Si la revue est validée, alors la branche est "mergée" dans la branche cible

* C'est le modèle poussé par GitHub !

== Forks ! Forks everywhere !

Dans la terminologie GitHub:

* Un fork est un remote copié d'un dépôt principal
** C'est la où les contributeurs poussent leur branche de travail.
* Les branches de version (main, staging...) vivent sur le dépôt principal
* La procédure de ramener un changement d'un fork à un dépôt principal s'appelle la Pull Request (PR)


== Checkpoint 🎯

* Git permet d'avoir plusieurs dépôts distants ("Remote")
** Par défaut : `origin`

* Git suit les branches locales ET distantes
** 💡 `git branch`

* `git fetch` permet de récupérer les historiques des dépôts distants
** 💡 `git pull <remote> <branch>` == +
  `git fetch <remote>` + +
  `git merge <remote>/<branch> <branch>`

* GitHub permet de "forker" un dépôt existant dans un nouveau dépôt personnel
** Vous pouvez ainsi avoir une seconde "remote" à suivre : `upstream`
